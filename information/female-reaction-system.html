The stat logic — which emotion moves, and the consent gate

  • Placer (arousal) — PlacerPorVerPartesMasculinas. Threshold asset umbralData.placer_Vision.mirando, body-part group erogenoVisual. Caps at placer-group max × 0.25 (maxEmocionValuePorGrupoMod = 0.25f), and that ceiling is lerped upward by her current arousal (OnPreLimitarMaxEmocionValue) — the more aroused she already is, the more just looking at him adds. ArousalPorOrgasmo later feeds Arousal when Placer maxes.
  • Rage — RagePorVerPartesMasculinas, body-part group privacidadVisual, entirely consent-gated in OnPreUmbralCalculo:
    • If ConsentNecesario.EsConsentidoConJerarquia(visual, dada, part, …, out necesario) → estimulacionGenerada.moded = 0. Consent ≥ required → zero rage, only the Placer path runs (she's into it).
    • Otherwise gap = |necesario − consentToHero·100|, and rage *= InverseLerp(0, 20, gap).OutPow(2f) — rage scales with the square of the consent shortfall, saturating once the gap reaches 20 points. Small shortfall → barely annoyed; ≥20 → full rage.
    • The required consent (necesario) is eased down by her arousal (concentVsArousal), so an already-aroused model tolerates exposure a cold one would rage at.
    • If consent was forced (ConsentCorrupted.EsCorrupted), MaximoAlcanzado caps rage where it is — it can't keep climbing.

This is the same value ≥ necesario gate as §5; the absolute base magnitudes live in each personality's MapaDeEmociones.asset (placer_Vision.mirando / rage_Vision.mirando) — the in-code coefficients are the 0.25 placer cap, the 90°/20° & 15m/0.2m lerps, the 0.333 geometry floor and the 0–20 consent-gap rage curve.

What you actually see — pose, not dialogue

  • Consenting / aroused → mouth & body desire poses: ReactorDeseoOralBocaPosePorVer (opens her mouth, sized by penis width), ReactorOralAtPorVerPene (mouth tracks it), ReactorSexAtPorVerPene (vagina/anus auto-aims toward it when in range). Arousal/placer bars rise.
  • Not consenting → Rage rises; cover-up / displeasure expression layers.
  • No bark. The dedicated ReactorDeBarkingPorVerPartesMasuculinas is an empty [Obsolete("", true)] stub, and the generic emotion-bark reactor (§7) only validates on recibida stimuli, not dada — so seeing the male undressed yields pose / gesture output, not a spoken line. (If a verbal/stat reaction to "shirtless" specifically is wanted, that is a content gap, not a bug.)

Note — the Camera Shop upgrade does not touch this path. MaleUpgrades.CameraLevel scales the being-photographed side only (CameraConsentMult on the photo-consent reactor, CameraArousalMult in PlacerPorSerVistoPorMain), i.e. the recibida family — not the PorVer "she sees him" family above.

3b · Sensitive spots — body-part tiers & why some models have "extra sensitive" areas

"This model is much more sensitive on her neck" is not stored as a per-spot number. Sensitivity is a two-level lookup: each body part is sorted into a tier group, and each tier carries an arousal-generation multiplier and a pleasure ceiling. A model gets an "extra sensitive" spot when her genetics roll shuffles a part into a higher tier than the default.

The touch→pleasure calculator (PlacerPorToques) never reads a "sensitivity" field off the collider. It asks which tier group the touched part is in, then multiplies by that tier's rate and clamps to that tier's max. Change the part→tier assignment and you have changed how sensitive that spot is — that is exactly the knob the per-model genetics randomizer turns.

The body parts — a named enum

Parts are the 42-value Spanish enum ParteDelCuerpoHumano (…/Base.Plugins/Assets/ParteDelCuerpoHumano.cs); the penetrable subset is the sibling ParteDelCuerpoHumanoHole (mouth / vag / ano). The touch system keys everything off these enum members:

The tier ladder — group → multiplier × ceiling

Each part is filed into a GrupoQueCompartenValores ("group that shares values") — an ordered tier enum f < e < d < c < b < a < aPlus. PlacerPorToques wires three dictionaries to it: the part→group map (erogeno), the per-group pleasure ceiling, and the per-group generation-rate multiplier (PlacerPorToques.cs:28,34,38). The actual lookup & multiply happen in the generic base CalculoDeEstimuloPorTactilesRecibidos (GetGrupoDeParte in PoblarConData, then AplicarModificadoresDeGeneracion, ~lines 244–256).

The numbers live in Assets/MonoBehaviour/ as sub-assets of MapaDeEmocionesDefault.asset: ErogenoGrupo.asset (the default part→tier map), ErogenoEstimuladoGrupoMod.asset (rate ×: f 0.333 … aPlus 3.0) and MaxPlacerPorGrupo.asset (ceiling: f 30 … aPlus 120). The same map holds parallel classifications used by other channels — seinsibilidad (tactile thresholds), erogenoVisual, privacidad, privacidadVisual (MapaDeEmociones.cs). There is also a hard-coded clitoris bonus (+100% generation, widened interval) in PlacerPorToques.cs:141-146, on top of its aPlus tier.

How per-model variation is generated — the genetics "Alteradores"

The default tier map is the starting point; on a per-NPC basis the genetics system re-buckets parts. The chain:

  • One randomizable knob per body part. AlteracionesDeErogenidadGrupoDeParteEstimulada builds an AlteradorDeGrupoQueCompartenValores for every ParteDelCuerpoHumano (names like Personalidad_Grupo_Erogenidad_ParteEstimulada_*), bound to Personalidad.SetGrupoDeErogenaEstimulable (Personalidad.cs:603-616). A sibling does the same for tactile thresholds (…SensibilidadGrupoDeParteEstimulada → seinsibilidad).
  • The knob treats the tier enum as an integer it can nudge. AlteradorDeGrupoQueCompartenValores (extends AlteradorDeEnumValueSinZero<…>) maps tier↔int so it can be shifted up/down (:26-34).
  • The randomization map drives the draw. MapaRamModFem_AltGruposQueComparenValores registers the erogeno-part holder with power 6 and the sensibilidad-part holder with power 9 (:16-27); OnApplyTo calls ModificadorSimpleParaNombre.Modificar per part, and the actual draw is Randomizado.Modificar via UnityEngine.Random.Range (clamped to the enum's min/max tier). Each model therefore gets a randomized tier per part, biased by those powers.
  • Wired into personality genetics via MapasDeModificacionDeRandomizadoDePersonalidadFemenina (asset line 18, guid 5392a61a…), so the roll runs whenever a female's personality is generated.

So "some models have extra sensitive areas" = the genetics roll pushed specific parts into a higher tier for that NPC — that spot now has both a much higher generation rate (up to ×3.0) and a higher pleasure ceiling (up to 120), so it arouses much faster. Two related global (not per-spot) knobs also vary per model: initial channel sensitivities (AlteracionesDeDeseosSensibilidadesIniciales.cs:44-75, tactile/visual/coital ×0.1–10) and randomized touch thresholds (AlteracionesDePlacerPorCaricias + MapaRamModFem_AltDeUmbrales).

Surfaced as a game feature: the dark-web "Deep Dive" (tier-3) dossier reports each model's 1–2 strongest ordinary zones as a suggestive ex-partner rumor — ranked by their measured per-girl strength (rolled cap × clamp(gain, 0.3, 2), §3c), not the tier letter, so the recommendation stays correct despite the per-girl roll. SMAGameplayController.SensitivityDescDesde reads modificadoresDeGeneradoPorGrupo.erogenoEstimulados + maxEmocionValuePorGrupo.placer off her cloned map (genitals excluded — top-tier on everyone). See docs/new-features.md → "The Onion".

Rebuild caveat: MapaDeEmocionesDefault.asset and the per-NPC personality components hold exactly the kind of List/array-on-generic-base data AssetRipper tends to strip (see §12). If a model ever spawns with every part in tier f (nothing feels sensitive), check those partes: lists for emptiness before suspecting logic.

3c · How a touch becomes arousal — the gain pipeline & the per-girl multiplier roll

§3b is the map (which tier each part is in). This is the runtime: once a part's tier is known, how a touch turns into an arousal gain — and the part that surprises people, that the per-tier multiplier and cap values are themselves rolled per girl, so two models with the same-tier spot don't gain the same.

Verified on a live model (bridge /sensprobe): the per-tier gain multiplier is applied — simulated per-frame gain came out as genMult × 0.0319, a constant ratio across all seven tiers (an aPlus spot generated ~12× an f spot). The multiplier is not stripped or bypassed. And the per-girl value scatter below is intended shipped design — the chain was checked byte-for-byte against the original IL, with no AssetRipper damage.

The two multipliers, and how each girl rolls them

  • Gain multiplier — applied in AplicarModificadoresDeGeneracion (CalculoDeEstimuloPorTactilesRecibidos.cs:244) as base *= estimulanteMult *= estimuladaMult via UmbralBasico.ModificarGenerado (*= mod). The estimulada (her body part) factor is the §3b tier value — authored ErogenoEstimuladoGrupoMod f 0.333 … aPlus 3.0.
  • Cap — MaximoAlcanzado caps Placer at the part's per-tier ceiling, authored MaxPlacerPorGrupo f 30 … aPlus 120.
  • Per-girl roll — neither value is fixed. At spawn, each tier is rolled independently from the authored baseline (read live; AlteradorGenericoConInicial.OnStart):
    • gain = authored × random ∈ [0.4, 2.5] (AlteracionesDeEstimulosGeneradosPorGrupoEstimulado)
    • cap = authored, within [authored ÷ 3, 121] (AlteracionesDeMaxEmocionPorGrupoDePlacer)
    • registered in MapaRamModFem_AltVariosDePersonalidad.
    Because each tier is drawn independently, monotonicity is not guaranteed — a higher tier can end up weaker than a lower one on a given girl.

Why a top-tier spot can still feel weak

  • Adjacent tiers overlap heavily. With a [0.4, 2.5] multiplier on each tier, a c spot rolls anywhere in 0.4–2.5 and a b spot in 0.5–3.1 — so neighbouring tiers are frequently indistinguishable. Only the extremes (f vs aPlus) stay reliably separated.
  • The cap floor is authored ÷ 3. A high-tier part can roll a near-dead ceiling (the model above: tier e capped at 19.5), so it stops rising almost immediately regardless of how strong its gain multiplier is.
  • The base gain is small and tier-independent (set by touch velocity vs the threshold interval), so the multiplier scales a modest number.

This is tuning, not a defect (IL-verified). Levers, all plain code literals: narrow the gain range (AlteracionesDeEstimulosGeneradosPorGrupoEstimulado 0.4f/2.5f), raise the cap floor (AlteracionesDeMaxEmocionPorGrupoDePlacer 1f/3f), or sort the rolled values to force monotonicity. The diagnostic that produced the table above is the bridge probe /sensprobe?part=&est= (SMANew/ExportedProject/Assets/Editor/ClaudeBridge.cs): on a live female it sets one part to each tier in turn, runs the game's own SimularGlobal, and reports gain vs. multiplier so you can see the scaling directly.

5Consent — the ceiling she stops at & the shield

ConsentToHero is one more Emocion (0–100, …/AI/Emociones/ConsentToHero.cs), but it is the one that gates whether an interaction is allowed at all. When the player pushes and she "wants to stop here," a shield icon appears over her consent bar — that is ConsentPorPlacerMaxIcon turning on because consent has reached the most she will grant this session.

The shield is just a read-out. ConsentPorPlacerMaxIcon.LateUpdate enables its Image when ConsentPorInteraciones.alMaximo == true (session-earned consent hit its cap) or ConsentToHero.valueAtMax == true (the emotion is pinned at 100). The real gating is the consent value versus what each act requires.

The consent stack — what sets her current consent

How the pieces work

  • Floor — ConsentToHero.minValue = MainChar.instance.concentAura (a flat global, ConfiguracionGeneral.femaleGamePlay.heroConcentAuraAdicional). Consent never falls below it.
  • Favorability floor — minimoLimiteValor, written by BuffOnMinFavorabilityValueEffecto to ≈ the consent the acts she has grown comfortable with require (SimularValor over ConsentNecesario.ParaConJerarquia), and reduced by fatigue (over-using a girl lowers her comfort). This is the persistent, relationship-built part of her resting consent.
  • Toward-you favorability — ±33 via BuffOnFavorabilityValueTowardCharacterEffecto, added on the EmocionHacia toward this specific player's ID (Mathf.Clamp(add·stacks, −33, 33)).
  • Player aura — EmocionAuraReceiver / EmocionAuraProducer: every ~60 s she reads the current main char's per-ReaccionHumana aura and copies its value/gain modifiers onto her own emotion. The player can passively carry a consent (or pleasure-gain) aura. This replaced the obsolete gusto-min component ConcentToHeroMinimoDeFemale, which scored the male's muscle/money/altura/package… against her maxConsentPorGustos — attraction now reaches consent through buffs/auras rather than that direct path.
  • Session gains — ConsentPorInteraciones: a separate accumulator added on top, driven by ReactorCambioDeConsentPorSessionesEnd each time a consented stimulus session ends (+ for pleasure, − for rage), weighted by channel — visualMod 0.333 · tactilMod 1.0 · coitalMod 1.5, so escalating acts climb ≈4.5× faster than looking. It is hard-clamped to [0, CurrentMaxConsentPorInteraciones()]; on reaching the cap, m_alMaximo = true (shield on) and the session-end reactor early-returns — no further stimulation adds consent.

The session cap itself: CurrentMaxConsentPorInteraciones() = modificableDeConsentPorSessiones.ModificarValor(maxConsentPorSessiones / 2.64) — a per-girl personality value (base 66 → ≈25, randomized ~20–30), liftable by buff/genetics modifiers.

11Reactor internals & the cover sub-system

Every reactor derives from a generic base chain: ReactorSegundario → ReactorPadre → ReactorACalculoDeEstimulo<T> (and ReactorPadreSinLogicaACalculoDeEstimulo<T> for pass-through nodes). They form a tree: MainReactorGenerico at the root forwards each frame's stimulus calculos down through pass-through padres (ReactorDeFrameGenerico, …SesionGenerico, …DeMasPrioridad) to the leaf reactors that actually act. A padre only forwards if it procs, so the pass-through nodes are authored to always proc (probabilidadPorSegundo = 100) — if any of them is starved, its whole subtree goes silent.

12AssetRipper fragility (SMANew rebuild notes)

This whole subsystem is unusually fragile under the AssetRipper decompile because its config and wiring live on generic base classes, which AssetRipper cannot reflect — it emits those component bodies empty — and, when an ancestor in a reactor's chain is generic, it truncates the serialized body at that ancestor, dropping even the leaf class's own fields. Four separate strips each broke a different part of it; all are fixed in the rebuild (see SMANew/REBUILD_DEVIATIONS.md and the memories).

Meta-lesson: the bugs cascaded. The probabilidad fix made the tree run, which then surfaced the two latent crashes (a null array and a config-flag-broken invariant) that had been dormant because nothing ever reacted. When a fix that re-enables a starved subsystem produces new NREs / InvalidOperationExceptions, suspect more generic-base strips finally being reached, not the fix — and verify the crashing method against the shipped IL (the first three were byte-identical: genuine latent bugs gated by stripped config, fixed with minimal guards, not rewrites).

The fourth strip (the bark paraReaccion) has a different signature worth remembering: it threw nothing — the leaf just silently failed its validity check and never fired, so the female was mutely un-reactive (the bark text simply never appeared). And the lost field was declared on the most-derived leaf, dropped only because an ancestor was generic — so when triaging a stripped reactor, inspect the leaf class's own serialized fields, not just the generic base's.
